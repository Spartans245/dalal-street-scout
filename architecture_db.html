DALAL STREET SCOUT — ARCHITECTURE + DATABASE

Added 2026-04-11  ·  SQLite backend (dalal_street.db)  ·  4 tables  ·  server-side tab filtering  ·  frontend per-tab fetch
Why the DB was added: Flat JSON files (stocks.json, signals_log.json) get fully overwritten on every pipeline run — a missed run (e.g. StopOnIdleEnd kill on Apr 6–7 crash days) means that day's data is permanently lost. The SQLite DB gives a permanent historical record. As a second benefit, the frontend previously fetched all 2,562 stocks as a 7.38 MB JSON blob and filtered in the browser — the DB enables server-side tab filtering so each tab click returns only ~40–300 rows.

SERVER API — DB-POWERED ENDPOINTS

GET /api/stocks?tab=X  NEW
Accepts tab query param: all · breakout · coiling · pre_cross · post_cross · pullback · trending · none
WHEN tab IS ABSENT OR "all"
Returns full in-memory state: all 2,562 stocks
Same as original /api/stocks — no DB query
Payload: ~7.38 MB
WHEN tab IS A STAGE NAME
① Query DB: SELECT ticker FROM eod_snapshots WHERE trading_date=(SELECT MAX…) AND stage=?
② Filter in-memory state['stocks'] to matching tickers
③ Returns subset with all fields intact (including chartPrices/chartDates for charts)
Payload: ~50–200 KB depending on stage
Fallback: if DB missing → in-memory stock.stage === tab filter
ALWAYS IN EVERY RESPONSE (both tab and non-tab)
stage_counts — {"breakout":98,"coiling":314,"post_cross":240,...} — full universe counts, not filtered by tab
total_count — total stocks in scan (2,562)
tab — echoed back when a tab param was given, so frontend knows what was returned
EXISTING ENDPOINTS (unchanged)
GET /api/evals → reads signals_log.json directly (not DB)
GET /api/evals/analytics → reads data/evals/analytics.json directly
GET /api/lifecycle → reads lifecycle_log.json directly
DB is an additive layer — no existing endpoints were modified
DB HELPER — db_tickers_for_tab(tab)
Opens DB in read-only mode (?mode=ro URI) — cannot accidentally corrupt data during a read
SQLite WAL mode — concurrent reads safe even while db_writer is mid-write
Returns None on any error → server falls back to in-memory filter gracefully
Called per request — no connection pool needed (SQLite handles concurrency fine at this scale)

FRONTEND — HOW PER-TAB FETCH WORKS

TWO-VARIABLE DESIGN
planStocks (full universe)
Set once per full /api/stocks load (startup + polling refreshes)
Always 2,562 stocks — never replaced by tab fetches
Used by: Plan view (stage pipeline counts, strong tiles), Search (ticker autocomplete), Watchlist, Score view, Strategy, Sector PE, Stage modal, Compare / Change detection
allStocks (current tab's slice)
Replaced on every tab switch via fetchTab(stage)
On "ALL" tab: restored from planStocks (no fetch needed)
Used by: Scanner table only — the vs() MCap filter, table rows, sort, pagination
TAB SWITCH SEQUENCE
① USER CLICKS TAB
setStage('breakout') called
Sets activeStage = 'breakout'
Calls fetchTab('breakout')
② FETCH
GET /api/stocks?tab=breakout
Server queries DB → 98 tickers
Filters in-memory state → 98 full records
Returns ~50 KB JSON
③ UPDATE STATE
allStocks = d.stocks (98 items)
planStocks untouched
serverStageCounts updated from response
④ RENDER
renderStages() called
Tab badges use serverStageCounts (full counts)
Table rows from allStocks (98 items)
No JS filter needed — data is pre-filtered
serverStageCounts — WHY IT MATTERS
When allStocks holds only 98 breakout stocks, a count like allStocks.filter(s=>s.stage==='coiling').length would return 0 — because coiling stocks aren't in allStocks anymore. The tab badges (POST-CROSS 240 · PRE-CROSS 1 · BREAKOUT 98 ...) would all show 0 except for the active tab.

serverStageCounts is populated from the stage_counts field that every /api/stocks response now includes. It always reflects the full universe, so the badges are always correct regardless of which tab is active or what's in allStocks.
